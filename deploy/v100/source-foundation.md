# Native V100 source foundation

This work follows the updated adaptive-inference specification, SHA256
`479727e5e112995c3f4edff88747365efc33da2fe676d4e58dd7faf32b31991a`.
The stack is a source-build candidate. Compilation, metadata import, native
SM70 object coverage and device/model qualification are separate evidence.
No old cu126 wheel result qualifies this combination.

The target is native Linux AMD64 Ubuntu 24.04, CPython 3.12 and eight V100 SXM2
GPUs. The separate Blackwell/GB10 image and dependency inputs remain unchanged.
The development container uses the existing pinned CUDA 12.9.2 Ubuntu 24.04 child
image. It already includes nvcc 12.9.86, cudart 12.9.79, cuBLAS/Lt 12.9.2.10,
Nsight Compute 2025.2.1.3 and Compute Sanitizer 12.9.79. Selected additional packages
and source revisions are recorded in [source-pins.json](source-pins.json).

The owned downstream Torch source commit is
`5ab14acbced0c33e6b6e8fdbc5b541b57487f7e1`, on top of the listed upstream
release. Its single [recorded patch](framework-patches/0001-relocatable-aten-config.patch)
fixes the ATen CMake package's include path: upstream embedded the random wheel
staging directory, producing a nonexistent consumer path and a different wheel
hash on repeated builds. The source template now derives the installed include
directory relative to the CMake package. Its compiler/kernel source is unchanged.
This packaging correction does not address compiler issue 6111901.
The producer pins the original/effective commits, exact patch bytes, deterministic
fork metadata and complete effective source inventory. A sparse fixture replay
reproduced the original candidate commit. The selected replacement records actual
precommit Spin/lintrunner checks and a fenced Test Plan while retaining detached
HEAD. No installed wheel or vendored library was patched. The BF65 candidate
remains historical evidence of the earlier incomplete source workflow.

PyTorch 2.14.1's CUDA12 build finds external CUB; there is no CCCL gitmodule
to patch. The source recipe explicitly selects one complete CCCL 3.5 include
installation for CUB, Thrust and libcu++. It builds NCCL from source and binds
both its matching headers and shared library through supported CMake inputs.
The inherited NVIDIA image's NCCL 2.27.3 packages must be removed: hints alone
allowed CMake to choose that different provider in the first rejected attempt.
Both CMake's CUDA architecture and Torch's architecture list select SM70.

Torch's private CUTLASS 4.6.1 gitmodule remains part of the pinned upstream
framework source. Application CUTLASS 4.8.1 is a separate header input for owned
SM70 kernels and its qualification probe. No CUTLASS classes cross this binary
boundary. Each role's actual source identity must appear in the build receipt;
the framework is not described as internally using CUTLASS 4.8.1.

The producer uses a bounded build container with source/object caches on
Warehouse storage. It does not modify an installed wheel, swap wheel-owned CUDA
libraries, or change the host driver. CUDA source build and application native
extensions must select the recorded CCCL/CUTLASS include roots explicitly; the
toolkit's older default headers are not qualification for the selected release.
Compiler flags, CMake cache, linked/loaded paths, source/submodule identities,
whole artifact hashes and CPU/device receipts remain required release inputs.

## Build stages

`Dockerfile.source-builder` supplies build tools, profilers and the pinned CUDA base.
The Python build lock is generated by `source_foundation.py render-build-tools`
from an actual native pip report. Its bootstrap lock comes from that same report.
Binary Torch/TorchVision/Triton/NVIDIA wheel providers are rejected from this
source-build tool closure. The separate runtime closure retains Triton 3.8.0
for existing import dependencies, with no SM70 Triton execution claim. It has
no binary Torch/TorchVision or NVIDIA/CUDA provider wheels. The framework wheel
is produced from canonical source with the selected native providers. The text
profile does not require TorchVision; its old CUDA 12.6 provider is not imported.

Lint tooling has a separate pinned environment. Spin 0.18 requires Click below
8.4, whereas the application's HF Hub requires at least 8.4.2. The lint environment
uses Spin 0.18, UV 0.11.15, lintrunner 0.12.7, cmakelint 1.4.1 and the pinned host
codegen prerequisites. The supported `spin quicklint -- -a <paths>` dispatches
actual `lintrunner -a` on the uncommitted patch before a fork commit. Its managed
Python 3.10.20 interpreter (20260510 build) has separate URL/bytes/SHA256 pins.
The framework/runtime stays on Python 3.12. The user's narrow immutable
release-wheel exception permits the release build while retaining the lint,
detached-HEAD, Test Plan and publication rules.

The final builder installs 124 exact Debian artifacts from the recorded bundle,
including cuDNN, Nsight Systems and their Ubuntu 24.04 dependencies. The base
image owns its other packages. [source-apt-amd64.json](source-apt-amd64.json)
records each added artifact's version, origin, bytes and SHA256; its companion
checksum file controls the offline installation. APT's signed-index SHA512
download identities were checked when producing this bundle. No package-index
resolution occurs in the generated image's build steps. Keep the external
artifact bundle: its pinned URLs support reacquisition, while cached artifacts
allow reproduction when a package disappears from an upstream archive.

The current stage interface is:

```bash
docker build --network=none \
  --build-context source_artifacts=/path/to/foundation-state/release \
  -f deploy/v100/Dockerfile.source-builder -t tensorfold-v100:source-builder-cu1292 .
# Run in the owned builder with /work state, /src project and /opt/tensorfold-native prefix mounts:
bash /src/deploy/v100/source_build.sh lint-prepare
bash /src/deploy/v100/source_build.sh acquire
bash /src/deploy/v100/source_build.sh prepare
bash /src/deploy/v100/source_build.sh nccl
bash /src/deploy/v100/source_build.sh framework
bash /src/deploy/v100/source_build.sh probes
bash /src/deploy/v100/source_build.sh export
# Build the installed development/verification image from those actual outputs:
docker build --network=none \
  --build-context source_artifacts=/path/to/foundation-state/release \
  --target verification -f deploy/v100/Dockerfile -t tensorfold-v100:source-development .
docker run --rm --network none tensorfold-v100:source-development \
  /opt/tensorfold-pins/source_foundation.py audit
```

Source acquisition and native NCCL compilation precede the framework stage.
The acquisition command uses the exact commits from the pins and the complete
recursive PyTorch gitmodules. The script initializes logs/receipts and captures
each raw tree before a build stage consumes it. The completed-build producer
verifies those bytes again, including declared checkout conversions. Ignored and
nonignored untracked source is refused except for explicit build/generated/cache
roles; actual generated source bytes are separately recorded. The canonical Ninja
graph and fourteen exact generator side outputs define generated paths. Source
symlinks remain within the inventoried closure. CCCL's single IDE-only compile
commands link is separately declared metadata. Malformed tracked FIFOs refuse
before blocking. A changed input tree or wrong provider cannot inherit old pins.
Keep source clones, downloads and object caches outside the project/Docker
context. The build caps Torch parallelism at four jobs; the current prototype
container is limited to four CPU cores and 36 GiB RAM. The settings are build
resource controls, not model-serving capacity or throughput claims.

The initial producer bootstrap used the pinned CUDA image and recorded Ubuntu
24.04 APT inputs to acquire the tool environment. Its exact added package bytes
were then frozen in the artifact bundle and the generated builder was rebuilt
with networking disabled. Python URL/hash locks retain resolver provenance;
their generated offline counterparts select the same local wheel bytes.
`source_foundation.py render-dockerfiles` owns both selected Dockerfiles.
The old wheel recipe remains `Dockerfile.cu126-reference` for historical controls.

The [additive media procedure](media-foundation.md) retains the original build
receipt and audited provider bytes while applying a separately identified audit
policy for source-built CPU consumer extensions. It preserves the previous
producer/installation evidence and verifies it before publishing the new audit
manifest. This does not claim that the existing framework was rebuilt under the
new audit producer or transfer any compiler/device/model qualification.

Acquire the exact `build-debs` and `python-wheels` inputs before building. Source
fork preparation also needs `lint-wheels` and its managed-Python/UV cache; first
acquisition may use the pinned public URLs, while the recorded lint rerun used
`UV_OFFLINE=1`. Compiler and image install stages consume frozen local inputs.
The external release bundle contains these inputs, the owned
`native` prefix, compiled `probes`, framework `wheels`, and `build-inputs`
receipts. Source clones, downloads and objects remain outside the image context.
The native prefix includes exact NCCL, CUTLASS and CCCL root/component license
materials under `licenses`; the ordinary prefix hash inventory covers them.
The export stage records the actual compiler binaries, CMake configuration,
whole wheel/native-prefix hashes and all source inventory identities. Git
source commits alone do not substitute for this completed-build receipt.

The image then verifies the actual wheel and native prefix against that receipt,
imports the installed framework, binds native provider versions/loaded paths,
and inventories its framework files and mapped libraries. The protected manifest
is `/opt/tensorfold-pins/v100-source-foundation.json`. `audit` rechecks those
actual bytes and loaded providers and emits `software_integrity=passed` only
on agreement. Its evidence class is `source-built-software-identity`, and
`release_qualified` remains false. Host-injected driver DSOs are recorded freshly
in the audit result; they are not asserted to be artifacts built into the image.
Run the audit as a separate process, as shown above, to keep its library-map
scope consistent. No environment boolean or version string proves provenance.

The installed application selects the same source NCCL through its supported
`TF_NCCL_LIB=/opt/tensorfold-native/nccl-2.32.3/lib/libnccl.so.2` input. The image
checks the real `tensorfold.cuda.comm._library()` path/version after installing
TensorFold. Torch's own RPATH alone does not configure that independent consumer.

The distinct in-process entrypoint is `source_foundation.py::audit_process(manifest,
pins)`, with private dictionaries decoded by `read_json` from the protected
manifest and `/opt/tensorfold-pins/source-pins.json`. It retains all sealed byte
checks and baseline/provider mappings, verifies the actual application NCCL
consumer, and rejects relocated known library families. Additional server/JIT
libraries are separately enumerated and hashed as process inputs; they are not
asserted to be image-owned. Its schema is
`tensorfold.v100-source-foundation-process-audit`, still software-only with
`release_qualified=false`. The separate CLI is `audit-process`; ordinary `audit`
keeps its strict image-construction behavior. Profile promotion must still bind
the caller's exact numerical/kernel/workload identities and live evidence.

Nsight Compute's package is 2025.2.1.3 while its CLI reports release 2025.2.1.0,
build 35987062. Compute Sanitizer's CUDA package is 12.9.79 while its CLI reports
release 2025.2.1.0, build 35969825. Preserve these distinct identities.

The first source configuration using inherited NCCL 2.27.3 was stopped after
inspection established the wrong provider. Its log and cache remain reference
evidence. The corrected attempt links the owned 2.32.3 source output. It is not
valid to repair the old binary by overriding a library after wheel installation.

## Required primitive and library gates

The maintained CUDA probes support `--metadata-only` without a device and return
77 for an unavailable V100 when a device run is requested. An exit77 is UNRUN.
A non-SM70 device refuses the device gate rather than substituting another GPU.

`cccl_primitives` checks native scan, stable radix key/value sort, compaction,
reduction, warp reduction and block scan/reduction against independent integer
oracles. It queries caller-owned temporary storage, serializes its reuse on one
stream, and exercises eager plus CUDA graph execution. Test sizes and actual
temporary bytes must be recorded; compile-only metadata is not a pass.

`libraries` binds header/runtime versions, a bounded 32 MiB caller workspace,
explicit FP16 operands with FP32 accumulation/output, column-major layouts and
SM70 CUTLASS TensorOp GEMM. It compares cuBLAS, cuBLASLt and CUTLASS on exact
integer-valued inputs in eager and captured execution. This fixture establishes
neither a winning runtime algorithm nor full-model numerical/performance quality.
Model-row/shape/layout/workspace comparisons remain Section 15 gates.

Execute the compiled probes on the real V100 with `--run`; the CUB probe also
accepts a bounded element count. Run memcheck/racecheck/initcheck/synccheck with
the pinned Compute Sanitizer, retaining every raw result and exit status. The
installed image's existing SM70 provider/family/current-stream/graph tests and
four/eight-rank NCCL tests remain required on this new stack. Old cu126 results
do not transfer. Full model correctness, quality, resources and representative
performance remain separate Section 21 gates.

## Compiler issue 6111901 remains a release gate

NVIDIA's CUDA 13.2.2 release notes identify a reconvergence defect introduced in
CUDA 12.8 for two or more nested divergence levels where convergence instructions
were elided. The public statement does not establish SM70 applicability or a
supported12.x backport. CUDA 13's fix does not restore SM70 offline compilation.

The `reconvergence_6111901` probe covers the actual selected-position control
class: a partial ten-ID tile, invalid/owned/unowned/partial pages, initialized
registers, four component branches, and exact integer/count oracles. It compares
ordinary nested control flow with an explicit-warp-convergence candidate.
This is a synthetic fixture, not NVIDIA's private reproducer. SASS BSSY/BSYNC
inventory and successful compilation do not prove correct reconvergence or a
validated mitigation. Actual V100 execution and a justified vendor/toolchain
disposition are required before release. A concrete unresolved gate remains
visible; the producer does not silently select an older serving library.
