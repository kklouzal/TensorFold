# Private Gemma native-up configuration prototype

This branch adds an unselected component-investigation entry, not a serving policy or public launch flag. Production Python callers, the existing `fused_up` signature and its four-warp/four-stage choice, down projection and MT4 policy remain unchanged. The first local SM120 native run compiled the kernels but failed an oracle-coordinate assertion. The corrected run passed all63 checks with no skips; installed ARM qualification and integrated Gemma performance remain pending. No performance gain or new serving policy is selected.

The private native `gemma_fused_up` method consumes the same admitted, owner-prepared bank/plan/nonoverlapping scratch fields as `fused_up`. Its final arguments are `n, k, slots, common, warps, stages`. It constructs original CT mode, tanh-GeGLU activation1,16-pair items and one K slice internally. Its only launch choices are warps2/4 and stages2/3/4; invalid choices fail before tensor validation or launch. The method shares all original tensor geometry/device/dtype/stride/alignment/extent validation. Calibration validity and scratch lifetime remain the admitted bank/plan owner's contract. No new quantization, scale conversion, shape clamp, split-K or error recovery is introduced.

Warp ownership, shared-copy stride, launch bounds and actual thread count use the same compile-time warp parameter. The ring size, prefill, wait immediate and buffer indices use the same stage parameter. Each result retains its original ascending K chain, MMA/calibration operations, BF16 gate/up storage, BF16 GELU-before-product, per16 amax/reduction and E4M3/E2M1 output. Every CTA participant retains the existing waits/barriers; masked rows do not return before them. Graph selection precedes capture and all bank/plan/scratch/module owners must outlive replay. The existing validator was extracted into a shared read-only helper; output Tensor handles are borrowed there rather than copied again. That refactor and extra compiled variants have real compile/artifact/host costs; binary identity or execution neutrality is not claimed.

`tests/test_gemma_cuda_moe_up_layout.py` is a standard-library-only check of owned copy/output ownership and ring indices. It covers both warp choices, all1..16 live pair counts and stage depths2..4 with1..129 K groups. It does not simulate CUDA's synchronization implementation or establish numerical/device performance.

`tests/cuda/test_gemma_cuda_moe_up_config.py` retains the existing independent prepared GEMMs, BF16 GeGLU and CPU CT quantizer oracle. The proposed30 native cases check every code/scale byte and final ordered output at minimum64-wide, actual704/2816 and ragged multi-item geometries, both uniform/nonuniform calibration forms, all six configurations, graph replay with changed routes/item counts/input data, and invalid configuration/tensor-plan metadata. No deliberate device-trap case is added. The existing Gemma native-A4 and generic16/64-pair oracle/graph suites remain relevant regression controls; their earlier results do not qualify this source.

The preserved native-v1 run collected 61 cases, with 53 passes, 8 failures and no skips. Every failure occurred at the public baseline's code-byte assertion before entering its six-configuration loop. The independent oracle incorrectly appended quantized rows in original selected-slot order. Native scratch is indexed by grouped-plan pair: ascending expert, then original flat pair `row * slots + slot`; down projection uses `members[pair]` to scatter back to the original row/slot. The correction derives that full ordering independently from CPU picks, asserts the complete native member vector equals it, and runs the unchanged GEMM/GeGLU/CPU quantizer in those coordinates. Two standard-library controls cover shuffled slots, multiple rows and duplicate experts. No runtime/kernel, numerical formula, tolerance, full-byte check or independent final-output oracle changed. Failed source18bd and its raw results remain preserved; the 12 passing private graph cases and other v1 passes do not qualify the blocked raw-byte loops.

All63 cases passed: five standard-library layout/order controls and58 CUDA cases comprising30 private-configuration cases, six original-CT controls and22 existing device-plan/replay controls. The run used CPUs0-7, eight intra-op threads, one inter-op thread, a16GiB container limit and two compiler workers. It retained full source/native-provider identities, consumed CUDA/runtime mappings, final device settlement and acknowledged container retirement; both independent actual reviews passed. The protected FD product and its recipe were declared but no FD consumer was exercised. These are functional results, not warm-kernel timings, a cold-compilation improvement, SM12.1 evidence or a full-model speed comparison.
